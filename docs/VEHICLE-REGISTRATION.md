# Vehicle and GPS registration

Open **Monitoring → Device Models** to create reusable profiles, then
**Monitoring → Vehicles → Register vehicle**. The GPS map's main registration
button opens the same combined flow. The advanced standalone GPS registration
screen remains available for existing installations and unassigned trackers.

The five steps collect vehicle identity/owner/map icon, GPS model and IMEI,
SIM/connectivity, operations/odometer baseline, and private attachments. IMEIs
are 15-digit strings, checked against both identifier and IMEI uniqueness.
Model profiles record manufacturer, protocol/version and device network
generation. SIM provider and SIM generation are separate. Airtel, Vi and Jio
are included; BSNL and Other are also available. Product serial, VTS reference,
firmware, ICCID, APN and reporting/heartbeat intervals can be stored.

The Vehicles page also includes paginated **Awaiting vehicle number** cards for
existing unassigned GPS devices, labelled by IMEI. **Add vehicle number** opens
the same form with the existing device prefilled. Saving creates the vehicle
and attaches that device under row locks; it never inserts a duplicate tracker.
A concurrent/repeated attempt cannot steal an assigned tracker or leave a second
vehicle. Initial completion retains the tracker's own unassigned last-known fix;
ordinary transfers between vehicles still clear the old position pointer.
Historical location rows are not rewritten. Device edits can be left unchecked
to retain its existing profile/configuration while adding just vehicle details.

Vehicle type/icon selection is shared by both dashboard and hardware GPS map
markers through an allowlisted icon payload. Existing bike/car profiles retain
their fallback icons. Odometer is a baseline in metres, with GPS/device/manual
source and optional engine-hours baseline; selecting a source does not invent
device/CAN readings or change how historic distance was calculated.

Create/update saves vehicle and tracker assignment transactionally using the
existing HardwareRegistrationService, including allowlist synchronization,
current-cache invalidation and assignment history. Failed saves remove their new
uploads. Existing registered device profiles can be kept without a catalog
model; unchecking device updates preserves the existing installation. Normal
editing does not create a second tracker or assignment.

Photos (JPEG/PNG/WebP), documents (PDF/JPEG/PNG) and other photos are separate
upload groups, each up to five files of five MB per submission, maximum fifty
attachments per vehicle. Files stay on the private local disk. Preview/download
uses authorized routes; no public storage link is needed. Edits retain previous
attachments unless explicitly removed; their private files are deleted after
the successful transaction. User-supplied attachment paths are ignored.

Vehicle index uses paginated searchable cards with photo, selected icon, status,
IMEI, model, SIM and driver. Details, edit and delete are available. Vehicle
deletion is a soft delete and disables its tracker, retaining historical GPS
and assignment records. It does not delete the physical hardware registration.
An installed catalog model cannot be deleted or have its protocol/version
silently changed: mark it inactive or create a new profile instead. Inactive
models are unavailable for new installations.

Live data starts after the **actual device** is configured to reach this server
and sends a valid supported packet. The current local listener is the registered
PT06 diagnostic receiver on TCP 9000. Catalog selection does not install a new
protocol decoder or reconfigure hardware remotely. Other implemented adapters
require the corresponding receiver deployment and hardware acceptance. GT05,
TK103 and other catalog-only profiles can be recorded inactive; activation
rejects unsupported protocol/version combinations. No fake coordinates are
created. The dashboard lists registrations without a fix as awaiting GPS.

## Deployment

The additive migration `2026_10_28_000002_add_fleet_registration_catalog` creates
the model catalog, nullable model FK on gps_devices, and vehicles.deleted_at.
Existing vehicle/device data remains intact. Migration is applied locally.
For another environment:

Deploy this additive migration before the new application code is loaded by
requests or rotating workers (stage the migration alone, then release the code).
This prevents a new Vehicle soft-delete scope querying a missing column.

```powershell
php artisan migrate --path=database/migrations/2026_10_28_000002_add_fleet_registration_catalog.php --force
npm.cmd run build
php artisan view:cache
```

Refresh long-running GPS workers after code deployment to load the new icon
payload; preserve the live TCP listener and shared Reverb. Windows helper:
`tools/start-gps-realtime.ps1 -Restart -WorkersOnly -KeepReverb`.

Local verification caught three gps-live failures caused by a worker loading the
new Vehicle scope before the column existed. After confirming the migration,
only those three recorded job UUIDs were retried. Health at 11:08:00 UTC showed
zero pending/reserved/failed GPS jobs, a fresh receiver heartbeat and signed
Reverb publish acceptance. The TCP receiver and shared Reverb were preserved.

Rollback application code/assets from the reviewed previous release before
considering schema rollback. Keep the additive columns and catalog if they have
new records. Dropping deleted_at could expose archived vehicles; dropping the
catalog loses model profiles. Never migrate:fresh or delete tracking history.
